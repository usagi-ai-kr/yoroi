# 프로젝트와 GitHub 운영

라벨은 [references/labels.md](references/labels.md),
초기 설정은 [references/setup.md](references/setup.md)를 읽는다.
브랜치·원격·필수 체크 이름은 호스트 문서에서 확인한다.

## 계획과 진척

1. 호스트 규칙·현재 변경·관련 기록을 확인한다.
2. 여러 단계 작업은 목표·완료 기준·의존성을 `plan` 기록에 적는다.
   작은 작업은 `work` 하나로 충분하다.
3. 의미 있는 진척·결정·막힌 점은 기존 기록에 추가하고 중복 이슈를 피한다.
4. 검증 후 결과·근거·남은 항목을 기록한다. 이슈 종료도 허가된 범위에서 수행한다.

GitHub 이슈·댓글·PR·설정 변경은 사용자 요청으로 허가된 범위에서 실행한다.
원격·인증·허가가 없으면 로컬 기록으로 진행한다. `memo`는 사람 전용이며 읽기만 한다.

## 이슈 종료

- 처리된 issue는 반드시 close한다. 완료 기준을 충족하면 PR 본문의 `Closes #번호`로 머지 시 자동 종료하거나, PR 밖에서 직접 close한다.
- 미완료 사유가 있으면 open으로 두고 사유를 1–2줄로 남긴다.
- PR 머지 뒤에야 끝나는 작업(예: 외부 게시)은 PR Closes에 넣지 않고, 완료 후 직접 close한다.
- memo 이슈는 close하거나 수정하지 않는다.

## 커밋과 PR

- 커밋·push·PR·머지의 시점과 허가는 호스트 규칙과 요청을 따른다.
- 커밋은 경로를 지정한 `git add <files>`로 한다. 사용자 변경과 섞이면 경로 제외로 충분하다.
- private index·manifest·해시 대조는 기본 절차가 아니라 필요할 때만 쓴다.
- 작업 트리·브랜치를 확인하고 기존 변경을 덮어쓰거나 강제로 동기화하지 않는다.
- 장기 dev → main 운영은 main을 dev에 동기화하고 검증한다.
- 같은 head/base의 열린 PR을 갱신하고 결과·검증·관련 이슈를 적는다.
- 주된 PR 라벨은 기능 `feature`, 수정 `fix`, 문서·스킬 `docs`다.
- 장기 dev 운영은 merge commit을 사용하고 dev를 삭제하지 않는다.
- CI 성공과 머지 허가를 확인한 뒤 요청된 머지를 수행한다.

```bash
gh pr list --base <base> --head <head>
gh pr create --base <base> --head <head> --title '<요약>' --body-file <본문파일>
gh pr checks <번호>
```

## 보고와 사람 조치

- 보고는 완료/진행/대기·근거·다음 작업을 적고 외부 기록 허가 시 `report` 이슈를 쓴다.
- 사람 조치는 필요 항목·이유·확인 방법을 `handle` 기록에 남긴다.
- 대기 작업은 `hold`, 재개 시 해제한다. 독립 작업은 계속한다.
- 시크릿 값은 이슈·댓글에 받지 않고 입력 위치만 안내한다.
- 여러 줄 본문은 파일에 작성해 `--body-file`로 전달한다.
