# 하네스 개선 및 장애 대응 정책 (Harness Improvement Policy)

## 1. 목적 및 정의
- **하네스 범위**: 에이전트 작업 환경을 구성하는 스킬(`.agents/skills/`), 운영 규칙(`AGENTS.md`), 보조 스크립트(`scripts/`), 운영 문서(`docs/`).
- **운영 원칙**: 실제 작업 중 관측된 하네스 결함·지연이 발생하면 별도 사용자 지시 없이 자율 진단하고 최소한의 재발 방지 개선을 즉시 적용한다.

## 2. 장애 트리거 및 대응 절차
1. **관측 트리거**:
   - `done + missing report`로 인한 불필요한 sleep·대기 지연
   - 완료 판정 지연 및 미완료(`working`)와 `no_report`의 혼선
   - 협업 패킷 전달 누락 또는 불필요한 자동 재전송
   - 검증 누락, 권한 흐름 병목, 파일 소유권 충돌
2. **4단계 개선 루프**:
   - **진단 (Diagnose)**: 실제 발생한 로그·패킷·상태를 분석하여 병목 원인을 규명한다.
   - **최소 수정 (Minimal Fix)**: 동일 문제의 재발을 차단하는 최소 범위의 규칙·스크립트·문서 패치를 작성한다.
   - **의미 검증 (Verify)**: 단위 검증, 문법 검사(`bash -n` 등), 구조 검증(`validate-repo.py`)을 전수 실행한다.
   - **회고 및 기록 (Record)**: 조치 내용과 재발 방지책을 `docs/` 및 관련 스킬에 기록하고 본 작업으로 복귀한다.

## 3. 메타 루프 방지 안전 가드레일
- **본 작업 우선**: 하네스 개선은 제품 목표 달성을 돕는 수단이며, 메타 개선 자체만 무한 반복하지 않는다.
- **1회 개선 루프 제한**: 단일 장애 건당 [진단 → 수정 → 검증 → 기록]의 1회 루프만 수행하고 즉시 본 작업을 재개한다. 단, 같은 장애의 검증 실패를 교정하는 bounded 수정·재검증은 루프 안에서 허용한다(새 장애·범위 확장 금지).
- **실제 관측 근거 필수**: 추측이나 가상 시나리오에 의한 과잉 개선은 금지하며, 실제 관측된 증거가 있을 때만 착수한다.
- **누적 대기 상한 준수**: 작업 감시 시 누적 대기 상한을 두고 최초 발송 시각을 기준으로 지연 여부를 판정한다.
- **권한 임의 확장 금지**: 하네스 개선을 구실로 사용자 승인 범위 확대, 외부 쓰기, 모델·패널 변경을 임의로 수행하지 않는다.
