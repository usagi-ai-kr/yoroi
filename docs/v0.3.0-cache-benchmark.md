# 0.3.0 SQLite 캐시 갱신 속도 — 합성 벤치마크

## 범위와 재현

- [#71](https://github.com/qus0in/yoroi/issues/71)의 캐시·이력 어댑터와 `CachedSource`·`collectOnce`를 실행한다.
- 합성 측정에서는 실계정·네트워크·공급자 CLI·Keychain·실제 HOME 데이터를 사용하지 않는다. 외부 호출 수는 합성 `read()` 횟수다.
- 실행: `node --import tsx scripts/bench-cache.mjs > /tmp/yoroi-cache-bench.json`.
- DB·가짜 HOME은 OS 임시 디렉터리에 만들고 종료 시 제거한다. 락 보유 자식도 종료·회수한다.
- 인프로세스 측정으로 Node/tsx 시작·CLI 렌더·composition의 Zen 조회 비용은 포함하지 않는다.
- 합성 조건·결과는 아래 표를 따른다. 실제 HOME의 CLI 기동 포함 측정은 마지막 「실계정 확인」 절에 따로 기록한다.

## 조건

- 공급자 5개를 `Promise.all`로 조회한다. 기본 합성 지연은 순서대로 2/4/8/16/32ms다.
- 각 지연에 `(roundIndex + providerIndex) % 4`의 0/1/2/3ms 지터를 더한다. roundIndex는 워밍업부터 0으로 시작한다.
  매 시나리오의 같은 round는 동일 입력이다.
- 시나리오별 워밍업 20회 제외 후 n=200. A→G 순서를 매 round 한 칸씩 회전해 시간 드리프트를 분산한다.
- 스냅샷 시계는 합성 UTC 시각에서 round별 100ms 전진한다. TTL은 실시간 대기 대신 이 시계로 제어한다.
- 분위수는 정렬 표본의 nearest-rank(`ceil(p*n)`)이며 단위는 ms다.
- wall은 DB open(해당 군)부터 병렬 조회·캐시/이력 처리·DB close까지다. 준비·검증·이벤트 루프 샘플 대기는 제외한다.
- 이벤트 루프는 `monitorEventLoopDelay({resolution:1})`를 각 실행 앞뒤 2ms 동안도 켠다.
  표의 loop는 각 실행 histogram의 p99를 모은 분포다. 1ms 샘플 간격이 포함되므로 순수 추가 지연과 다르다.
- 1개 창/공급자, 같은 비밀 없는 scope/contract, SQLite WAL, usage busy_timeout 100ms를 사용한다.

| 군 | 의미·측정 범위 |
| --- | --- |
| A | 캐시 없음: 원본 합성 source만 조회 |
| B | 빈 DB miss: 매번 DB 디렉터리를 측정 밖에서 제거하고 open·v1/v2 생성부터 측정 |
| C | 기존 DB miss: TTL 정확히 60,000ms 지난 행을 미리 준비; 재open·조회·저장·close |
| D | 전부 hit: 5개 fresh 행을 미리 준비; 재open·캐시/이력 읽기·close, 원본 read 0회 |
| E | 5개 중 1개 miss: 가장 느린 5번째 공급자만 만료; 나머지는 hit |
| F | DB 실패 폴백: 디렉터리 대신 파일인 경로에서 실제 open 실패 후 원본 source 조회 |
| G | 락 경합: 별도 프로세스가 BEGIN IMMEDIATE를 유지; 미리 연 usage 연결로 4개 hit·1개 miss 처리 |

- B는 DB만 새것이며 OS 파일 캐시·Node 모듈은 warm이다. C/D/E의 행 준비는 측정 밖이다.
- G는 open·close를 제외한다. 부모의 타이머로 락을 풀지 않으며 마지막 측정 이후 IPC로 해제한다.
  1개 캐시 쓰기와 1개 이력 쓰기가 각각 잠금 대기를 겪으므로 한 요청의 100ms가 전체 상한은 아니다.
- 모든 실행에서 동일한 성공 창 값·공급자 순서·군별 원본 read 수를 assert한다.
  G의 hit 4개는 시작 시각의 스냅샷을 계속 사용하며 원래 관측 시각 보존도 assert한다.

## 해석·한계

- 합성 지연은 실계정 지연의 추정값이 아니다. 실계정 확인에서도 공급자별 분포·인증·프로세스 기동 비용은 분리 계측하지 않았다.
- E는 느린 공급자가 miss인 경우만 다룬다. 어느 공급자가 miss인지에 따라 전체 지연이 달라진다.
- G는 장시간 writer lock을 유지한 스트레스 조건이다. 실제 writer가 빨리 종료되면 대기도 줄어들 수 있다.
- 여러 프로세스 동시 once, 큰 이력, SQLite 파일 손상, 전체 CLI 기동·출력 비용은 이번 통계 범위 밖이다.
- 비용 비교의 의미를 유지하려면 동일 하드웨어·Node·부하에서 스크립트를 다시 실행한다.
- 다른 worker의 CPU·I/O 부하는 통제하지 않았다. n=200의 p99는 제한된 꼬리 표본이며 성능 보장이 아니다.
