# 0.3.0 캐시·관측 이력 설계 ([#71](https://github.com/qus0in/yoroi/issues/71), [#72](https://github.com/qus0in/yoroi/issues/72)와 단일 yoroi.db)

> 준비 단계: 구현·의존성 설치·마이그레이션 적용 금지. 근거: [#71](https://github.com/qus0in/yoroi/issues/71), [#72](https://github.com/qus0in/yoroi/issues/72) DB 설계,
> `docs/v0.2.0/cache-design.md`·`sqlite-schema.md`, `src/infra/sqlite/*`, `src/domain/usage.ts`.

## 1. 범위·저장소 경계

- [#72](https://github.com/qus0in/yoroi/issues/72)와 같은 파일 `$YOROI_DATA_DIR/yoroi.db`(기본 `${XDG_DATA_HOME:-~/.local/share}/yoroi/yoroi.db`)에
  테이블만 추가한다. 경로·권한(디렉터리 0700, 파일 0600)·연결 정책(`node:sqlite`, WAL,
  `busy_timeout` 2000ms, `schema_migrations` 순차 적용)은 [#72](https://github.com/qus0in/yoroi/issues/72) 구현을 상속한다. 시각은 ISO 8601 UTC TEXT.
- TTL 캐시 `cache_entries`와 영구 이력 `observation_samples`는 테이블을 분리한다.
  캐시 만료·삭제·손상은 이력을 지우지 않고, 캐시 미스가 외부 수집을 유발하지 않는다.
- 캐시 키·이력·로그 어디에도 API 키·토큰·Authorization 헤더·원본 응답을 저장하지 않는다.

## 2. 마이그레이션 v2 DDL (v1은 [#72](https://github.com/qus0in/yoroi/issues/72) provider_locks/lock_events)

```sql
CREATE TABLE cache_entries (
  key TEXT PRIMARY KEY,             -- §3 키 규칙, 비밀 미포함
  value TEXT NOT NULL,              -- 정규화 성공 스냅샷만 직렬화
  observed_at TEXT NOT NULL,        -- 원래 실측 시각 그대로
  expires_at INTEGER NOT NULL       -- observed_at + 60000 epoch ms
);
CREATE INDEX idx_cache_expires ON cache_entries(expires_at);

CREATE TABLE observation_samples (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  provider TEXT NOT NULL,           -- usage.ts의 5개 provider
  account_scope TEXT NOT NULL,      -- 인증 프로필 단축 해시(원문 금지)
  contract_version TEXT NOT NULL,   -- sourceVersion/계약 버전
  window_id TEXT NOT NULL, unit TEXT NOT NULL, observed_at TEXT NOT NULL,
  period_start TEXT, reset_at TEXT,
  used REAL, remaining REAL, limit_value REAL, percent REAL,
  CHECK(used IS NULL OR used >= 0), CHECK(remaining IS NULL OR remaining >= 0),
  CHECK(limit_value IS NULL OR limit_value >= 0),
  CHECK(percent IS NULL OR (percent >= 0 AND percent <= 100)),
  UNIQUE(provider, account_scope, contract_version, window_id, unit, observed_at)
);
CREATE INDEX idx_obs_latest ON observation_samples(provider, account_scope, window_id, observed_at DESC);
CREATE INDEX idx_obs_reset ON observation_samples(provider, reset_at);
```

## 3. 캐시 키 구성 (비밀 미포함)

- 키: `cache:v1:{provider}:{lookup}:{scope}:{contract}`.
  `lookup`은 조회 방식+입력 정규화(예 `window:5h`, `windows:all`, `history:from..to`),
  `scope`는 인증 프로필 식별자의 단축 해시(예 SHA-256 앞 12 hex)나 비민감 라벨,
  `contract`는 `sourceVersion`/계약 버전이다. provider·입력·프로필·계약 중 하나라도 다르면 다른 키다.
- Keyv 네임스페이스를 쓰더라도 같은 접두를 사용하고, 자격 증명 원문은 키 재료로 쓰지 않는다.

## 4. TTL 60초 경계

- hit 조건: `now < expires_at`(`observed_at + 60_000ms`). 59초 재조회는 hit, 정확히 60,000ms부터 miss다.
- hit 응답은 `observedAt`을 원값으로 유지하고 `cacheHit`·경과 초를 표시해 실시간 조회로 오인하지 않게 한다.
  CLI 프로세스가 재시작돼도 같은 DB에서 hit가 유지된다.
- miss(만료·키 없음·`--refresh`)에만 외부 조회를 실행한다. 성공만 저장하고 타임아웃·인증 오류·HTTP 실패는 캐시하지 않는다.
- 같은 키 동시 호출은 in-flight promise 1개로 병합한다. 429/`Retry-After`와 공급자별 호출 간격 정책을 우회하지 않는다.
- 캐시 읽기 오류·파일 손상·SQLite busy 시 해당 provider만 오류 격리하고, 제한적 직접 조회 fallback 외에는 이력·타 공급자에 전파하지 않는다.

## 5. 이력 기록과 변화량·reset 판정

- `observation_samples` INSERT는 외부에서 실제 수집한 성공 스냅샷 경로에서만 한다.
  cache hit와 `watch`의 동일 캐시 재사용은 기록하지 않는다. 중복은 UNIQUE + `INSERT OR IGNORE`.
- 비교쌍은 같은 `(provider, account_scope, contract_version, window_id, unit)`의 직전 실측 행만이다.
  `period_start`/`reset_at`으로 다른 한도 기간임이 확인되거나 contract가 다르면 비교하지 않는다.

| 상황 | 표시 | 이력 |
| --- | --- | --- |
| 새 창(초기화, `reset_at`/`period_start`가 이전보다 미래로 이동) | `reset` | 관측 행 저장 |
| `reset_at` 과거 이동·소실, 필수 값 누락 | `n/a` | reset_anomaly/누락 사유 코드 |
| unit·contract 변경 | `n/a` | unit_mismatch, 변환 추정 금지 |
| 비교 가능 | `Δ = 현재 - 직전 실측` | 정상 |

- Δ는 절댓값+부호를 유지한다: `+4.2%p`, `-0.35 USD`, `+1,200 tokens`, 시간차 `+4.2%p / 2h`.
- `percent` 변화는 %p(절대차)이며 백분율 변화율과 구분한다. 모델·공급자의 서로 다른 단위를 합계로 단정하지 않는다.

## 6. Keyv 저장소 선택지 비교와 권고

| 항목 | A: `@keyv/sqlite`(better-sqlite3) | B: node:sqlite 커스텀 store |
| --- | --- | --- |
| 의존성 | native 모듈 추가, 빌드/prebuilt 리스크 | 추가 없음(Node 24 내장) |
| DB 파일 | 캐시 전용 파일 분리로 드라이버 이중화 | 같은 yoroi.db·PRAGMA·0600/0700 정책 재사용 |
| 동시성 | 별도 연결·WAL 정책 중복 관리 | `openDatabase` 재사용, 프로세스 간 단일 정책 |
| 구현 비용 | TTL·네임스페이스 즉시 사용 | Keyv `Store` 계약·만료 로직 직접 구현·테스트 |
| Keyv 연동 | 공식 store | 순수 JS `keyv` 코어에 store 주입 |

- 권고: **B**. [#72](https://github.com/qus0in/yoroi/issues/72)의 "네이티브 의존성 없음" 결정과 일관되고 단일 DB·권한 정책을 공유한다.
  `keyv` 코어 의존성 추가 여부는 구현 이슈 승인 시 정하고, 캐시 포트를 분리해 Keyv 없이도 교체 가능하게 한다.

## 7. 테스트 계획 (구현 시)

- Node test runner + 임시 파일 DB(0.2.0 §6: OS 임시 디렉터리, 종료 시 `-wal`/`-shm` 포함 제거), 가짜 시계 주입.
- TTL 경계: 최초 요청 → t+59,999ms hit(외부 호출 0회) → t+60,000ms miss → 재시작 후 hit 유지 → `--refresh` miss.
- 계약: 동일 키 동시 N회 → 외부 1회(in-flight), provider/프로필/contract 키 격리, 프로필 전환 시 다른 캐시,
  실패(타임아웃·401·5xx·파싱) 미캐시.
- 이력: cache hit·TTL 만료·캐시 행 삭제 후에도 이력 행 수 불변. 재수집 성공만 행 추가.
- 변화량 fixture: 증가/감소, reset(미래 이동), 누락·단위 변경·비교 불가 → `reset`/`n/a`, %p·부호·시간차 표기.
- 안전·회귀: 0600/0700, WAL·busy_timeout, 캐시 손상·busy 격리, 기존 5개 provider CLI 회귀.
